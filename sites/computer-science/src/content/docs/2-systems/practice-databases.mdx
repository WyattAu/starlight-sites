## Intuition

**Organising information like a filing cabinet:** Databases are like a well-organised filing cabinet — normalisation removes duplicate folders, SQL is the language for asking the librarian questions, and indexes are like a card catalogue that lets you find files without opening every drawer.

**Why it matters:** Every application with persistent data needs databases. Understanding normalisation prevents data corruption, indexing makes queries fast, and ACID properties keep your bank balance correct even when thousands of transactions happen simultaneously.

**The key insight:** Normalisation trades storage space for correctness — by eliminating redundancy, you eliminate the possibility of inconsistent data, but you may need joins (which are slower) to reassemble related information.

## SQL and Normalization

<PracticeProblem client:only="solid-js" question={"Which SQL clause filters aggregated results after grouping, as opposed to filtering individual rows before grouping?&quot; options={[ 'HAVING filters after GROUP BY; WHERE filters before GROUP BY', 'WHERE filters after GROUP BY; HAVING filters before GROUP BY', 'Both WHERE and HAVING filter before GROUP BY', 'Neither filters aggregated results; you must use a subquery', ]} correctAnswer={0} explanation=&quot;WHERE applies to individual rows before aggregation (filtering input to GROUP BY). HAVING applies to groups after aggregation (filtering the result of GROUP BY). Example: SELECT dept, AVG(salary) FROM emp GROUP BY dept HAVING COUNT(*) > 5 filters departments with more than 5 employees."} difficulty="easy"  />

<PracticeProblem client:only="solid-js" question={"A relation $R(A, B, C, D, E)$ has functional dependencies $AB \\to C$, $C \\to D$, and $D \\to E$. Which normal forms are violated?&quot; options={[ '3NF and BCNF are violated (transitive dependencies $C \\to D \\to E$)', 'Only 2NF is violated', 'Only BCNF is violated; 3NF is satisfied', 'The relation is already in BCNF', ]} correctAnswer={0} explanation=&quot;The candidate key is $\\{A, B\\}$. There are no partial dependencies (since AB is the key, and $C$ depends on all of AB). However, $C \\to D$ and $D \\to E$ are transitive dependencies: non-prime attributes $D$ and $E$ depend on $C$ rather than directly on the key. This violates 3NF (and BCNF). Decompose into $R_1(A,B,C)$, $R_2(C,D)$, $R_3(D,E)$."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"Boyce-Codd Normal Form (BCNF) requires that for every non-trivial functional dependency $X \\to Y$ in a relation:&quot; options={[ '$X$ must be a superkey', '$X$ must be the primary key', '$Y$ must be a prime attribute', '$X$ must contain at least one prime attribute', ]} correctAnswer={0} explanation=&quot;BCNF is stricter than 3NF: for every non-trivial FD $X \\to Y$, $X$ must be a superkey (a superset of some candidate key). 3NF allows $X \\to Y$ if $Y$ is a prime attribute, even when $X$ is not a superkey. BCNF decomposition may cause lossless-join issues that 3NF decomposition avoids."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"In the relational algebra expression $\\sigma_{\\text{dept}='CS'}(\\pi_{\\text{name, gpa}}(\\text{Students}))$, in what order are the operations applied?&quot; options={[ 'Projection first, then selection (inside out)', 'Selection first, then projection', 'Both are applied simultaneously', 'The order depends on the query optimizer', ]} correctAnswer={0} explanation=&quot;Relational algebra is applied inside-out (like nested function calls). First, $\\pi_{\\text{name, gpa}}(\\text{Students})$ projects only the name and gpa columns from Students. Then, $\\sigma_{\\text{dept}='CS'}$ filters the projected result. A query optimizer might push the selection down before projection for efficiency (selection pushdown), but the expression as written applies projection first."} difficulty="easy"  />

<PracticeProblem client:only="solid-js" question={"Armstrong\'s Axioms for functional dependencies include reflexivity ($Y \\subseteq X \\Rightarrow X \\to Y$), augmentation ($X \\to Y \\Rightarrow XZ \\to YZ$), and transitivity ($X \\to Y, Y \\to Z \\Rightarrow X \\to Z$). Which derived rule states that $X \\to Y$ and $X \\to Z$ implies $X \\to YZ$?&quot; options={['Union rule', 'Decomposition rule', 'Pseudotransitivity rule', 'Reflexivity rule']} correctAnswer={0} explanation=&quot;The union rule: if $X \\to Y$ and $X \\to Z$, then $X \\to YZ$. Proof: from $X \\to Y$, by augmentation with $Z$: $XZ \\to YZ$. Since $X \\to Z$, by augmentation with $X$: $XX \\to XZ$, i.e., $X \\to XZ$. By transitivity: $X \\to YZ$. The decomposition rule is the reverse: $X \\to YZ$ implies $X \\to Y$ and $X \\to Z$."} difficulty="medium"  />

## Indexing, Transactions, and Query Optimization

<PracticeProblem client:only="solid-js" question={"A B+ tree of order $d$ stores keys in internal nodes and all values in leaf nodes connected as a linked list. What makes B+ trees particularly efficient for range queries?&quot; options={[ 'Leaves are linked, allowing sequential scan after finding the start key in $O(\\log_d n)$', 'Internal nodes store all data, enabling direct access', 'Hash-based lookups provide $O(1)$ range access', 'Bitmap indexes are used for range scans', ]} correctAnswer={0} explanation=&quot;B+ tree leaves are connected via pointers forming a linked list in sorted order. A range query first finds the starting key in $O(\\log_d n)$, then scans sequentially through the leaf list. Total cost: $O(\\log_d n + k)$ where $k$ is the number of results. The parameter $d$ is chosen so one node fits in a disk block."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"Under the REPEATABLE READ isolation level, which anomaly is still possible?&quot; options={[ 'Phantom reads (new rows appear in a repeated range query)', 'Dirty reads (reading uncommitted data)', 'Non-repeatable reads (same query returns different results within a transaction)', 'Both dirty reads and non-repeatable reads', ]} correctAnswer={0} explanation=&quot;REPEATABLE READ prevents dirty reads (no uncommitted data) and non-repeatable reads (locks acquired on read rows prevent modifications). However, it does not prevent phantom reads: new rows inserted by another transaction into the range of a repeated query will appear, because the locks are on existing rows, not on gaps in the range."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"In Multi-Version Concurrency Control (MVCC), how are readers and writers handled to avoid blocking?&quot; options={[ 'Readers see a consistent snapshot (old version); writers create new versions without blocking readers', 'Both readers and writers acquire exclusive locks on rows', 'Readers block writers and writers block readers', 'Only one transaction can access any row at any time', ]} correctAnswer={0} explanation=&quot;MVCC maintains multiple versions of each row with version start/end timestamps. Readers see the version that was current when their transaction began (snapshot isolation), while writers create new versions. This eliminates reader-writer blocking. Garbage collection removes old versions no longer visible to any active transaction. Used by PostgreSQL and MySQL InnoDB."} difficulty="hard"  />

<PracticeProblem client:only="solid-js" question={"Which join algorithm has cost $O(|R| + |S|)$ and is most efficient when one relation fits entirely in memory?&quot; options={['Hash join', 'Nested-loop join', 'Sort-merge join', 'Block nested-loop join']} correctAnswer={0} explanation=&quot;The hash join has two phases: build (hash all tuples of the smaller relation $R$ into a hash table) and probe (scan $S$ and look up matches). Cost is $O(|R| + |S|)$. It requires $O(\\min(|R|, |S|))$ memory for the hash table. Nested-loop is $O(|R| \\cdot |S|)$. Sort-merge is $O(|R|\\log|R| + |S|\\log|S|)$."} difficulty="hard"  />
<PracticeProblem client:only="solid-js" question={"Bitmap indexes are most appropriate for columns with which characteristic?&quot; options={[ 'Low cardinality (few distinct values)', 'High cardinality (many distinct values)', 'Continuous numeric values', 'Variable-length text data', ]} correctAnswer={0} explanation=&quot;Bitmap indexes store one bitmap per distinct value, where each bit represents whether a row has that value. For low-cardinality columns (e.g., gender, status flags), this is efficient: few bitmaps, fast bitwise AND/OR for queries. For high-cardinality columns, the number of bitmaps grows prohibitively. B+ tree or hash indexes are better for high-cardinality data."} difficulty="easy"  />

## Common Mistakes

**Confusing normalisation with denormalisation:** Normalisation eliminates redundancy. Denormalisation adds redundancy for performance. Don't assume normalisation is always better.

**Forgetting that NULL is not a value:** NULL represents missing data. Comparisons with NULL return NULL, not true or false. Use IS NULL instead.

**Mixing up cursor-based with cursor-free pagination:** Cursor-based uses a pointer for efficient pagination. Cursor-free (OFFSET) skips rows, which gets slower with large offsets. Don't assume OFFSET is efficient for deep pagination.
