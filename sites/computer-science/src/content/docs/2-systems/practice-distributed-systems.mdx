10 MCQ questions covering the CAP theorem, consistency models, Paxos/Raft consensus, replication
strategies, fault tolerance, and logical clocks. Select an option to check your answer.

## Intuition

**A team of chefs in different kitchens:** Distributed systems are like a team of chefs working in different kitchens trying to prepare the same meal — they need to communicate, agree on the recipe (consensus), handle it when someone's oven breaks (fault tolerance), and serve the dish at the same time (consistency).

**Why it matters:** Every large-scale system — Google, Amazon, blockchain — is distributed. Understanding CAP theorem, consensus, and replication explains why these systems behave the way they do and what trade-offs they make.

**The key insight:** In distributed systems, you can't have everything — the CAP theorem forces you to choose between consistency, availability, and partition tolerance, and real systems must pick which compromise fits their use case.

<PracticeProblem client:only="solid-js" question={"What is the key difference between linearizability and sequential consistency?&quot; options={[ 'Linearizability requires operations to appear in real-time order; sequential consistency only requires program order per process', 'Sequential consistency is stronger than linearizability', 'Both are identical in terms of guarantees', 'Linearizability allows operations to be reordered but sequential consistency does not', ]} correctAnswer={0} explanation=&quot;Linearizability (strong consistency) requires that every operation appears to execute atomically at a single point in real time. <PracticeProblem client:only="solid-js" question={"In causal consistency, which operations must be seen in the same order by all processes?&quot; options={[ 'Only causally related operations; concurrent operations may appear in different orders', 'All operations must appear in the same total order', 'No ordering guarantees are provided', 'Only write operations must be ordered', ]} correctAnswer={0} explanation=&quot;Causal consistency ensures that if operation $a$ causally precedes operation $b$ (e.g., $a$ is a read and $b$ is a write that depends on $a$'s value), then all processes see $a$ before $b$. <PracticeProblem client:only="solid-js" question={"In leaderless replication with quorum reads and writes, the condition $W + R > N$ guarantees:&quot; options={[ 'At least one node has both the latest write and is consulted during the read', 'All replicas are always consistent', 'No data is ever lost during partitions', 'The system achieves linearizability', ]} correctAnswer={0} explanation=&quot;With $N$ total replicas, $W$ write replicas, and $R$ read replicas, the condition $W + R > N$ ensures the read set and write set overlap by at least one node. ## Consensus, Replication, and Fault Tolerance

<PracticeProblem client:only="solid-js" question={"In the Raft consensus algorithm, what mechanism prevents split votes during leader election?&quot; options={[ 'Randomized election timeouts (150-300ms)', 'Fixed election timeouts for all nodes', 'The leader pre-assigns votes to followers', 'A designated vice-leader always wins ties', ]} correctAnswer={0} explanation=&quot;In Raft, if multiple followers start elections simultaneously, they could split the vote and no candidate achieves majority. <PracticeProblem client:only="solid-js" question={"A system that tolerates $f$ Byzantine (arbitrary) failures requires a minimum of how many total replicas?&quot; options={['$n \\geq 3f + 1$', '$n \\geq 2f + 1$', '$n \\geq f + 1$', '$n \\geq 4f + 1$']} correctAnswer={0} explanation=&quot;For crash failures, $n \\geq 2f + 1$ suffices (majority of honest nodes). <PracticeProblem client:only="solid-js" question={"In the Paxos consensus protocol, Phase 1 (Prepare/Promise) ensures that:&quot; options={[ 'The proposer learns the highest-numbered previously accepted value (if any) and no higher proposal can supersede it', 'The value is immediately committed', 'All acceptors agree on the value without further communication', 'The proposer is elected as the permanent leader', ]} correctAnswer={0} explanation=&quot;In Paxos Phase 1, the proposer sends PREPARE($n$) to a majority. <PracticeProblem client:only="solid-js" question={"The Two-Phase Commit (2PC) protocol for distributed transactions has a critical flaw. <PracticeProblem client:only="solid-js" question={"Vector clocks solve a limitation of Lamport logical clocks. <PracticeProblem client:only="solid-js" question={"The CALM theorem states that consistency is equivalent to a specific property in distributed programs. Non-monotonic programs (e.g., those with deletes or negation) require coordination protocols to maintain consistency."} difficulty="hard"  />

<PracticeProblem client:only="solid-js" question={"What is the Gossip protocol and why is it used in distributed systems?&quot; options={[ 'An epidemic-style protocol where each node periodically shares state with random peers, providing eventually consistent replication with high fault tolerance', 'A consensus protocol requiring a designated leader for all decisions', 'A protocol for establishing causal ordering of events across processes', 'A protocol for mutual exclusion in critical sections', ]} correctAnswer={0} explanation=&quot;Gossip protocols mimic epidemic spread: each node periodically picks a random peer and exchanges state. <PracticeProblem client:only="solid-js" question={"In CRDTs (Conflict-free Replicated Data Types), what mathematical property ensures that concurrent updates can always be merged without conflict?&quot; options={[ 'Commutativity, associativity, and idempotency of the merge operation', 'Strict total ordering of all operations', 'Consensus among all replicas before applying updates', 'Two-phase commit across all replicas', ]} correctAnswer={0} explanation=&quot;CRDTs guarantee convergence through algebraic properties: the merge operation must be commutative ($a \\sqcup b = b \\sqcup a$), associative ($(a \\sqcup b) \\sqcup c = a \\sqcup (b \\sqcup c)$), and idempotent ($a \\sqcup a = a$). ## Common Mistakes

**Confusing consistency with availability:** Consistency means all nodes see the same data. Availability means every request gets a response. CAP theorem forces a trade-off during partitions.

**Assuming eventual consistency is always acceptable:** Eventual consistency may be fine for some applications but not for financial or medical systems. Consider your consistency requirements.

**Forgetting that consensus requires majority:** Paxos and Raft require a majority of nodes to agree. A minority partition cannot make progress. Don't assume all nodes can always participate.
