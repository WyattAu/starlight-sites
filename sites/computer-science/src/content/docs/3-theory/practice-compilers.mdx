10 MCQ questions covering lexical analysis, parsing (LL and LR), abstract syntax trees, intermediate

## Intuition

**A translator for translators:** A compiler is like a multi-stage translation pipeline — it first breaks your code into words (lexing), then checks the grammar (parsing), then rewrites it for clarity (optimisation), and finally converts it to machine language. Each stage catches different errors.

**Why it matters:** Compilers turn human-readable code into efficient machine instructions. Understanding them explains why some code is faster than others, how language features work under the hood, and why certain errors only show up at runtime.

**The key insight:** Compiler optimisations must preserve what your program does, not how it does it — they can rearrange, combine, and eliminate code, but the observable behaviour must stay the same.

## Lexical Analysis and Parsing

<PracticeProblem client:only="solid-js" question={"In lexical analysis, the 'maximal munch' rule resolves ambiguity by always:&quot; options={[ 'Matching the longest possible token from the current position', 'Matching the first valid token type in the grammar', 'Matching the shortest possible token to save memory', 'Preferting keywords over identifiers regardless of length', ]} correctAnswer={0} explanation=&quot;Maximal munch: the lexer always matches the longest valid prefix as a single token. For example, '123abc' is tokenized as '123' (integer) then 'abc' (identifier), not '1', '2', '3', 'abc'. This is implemented by running the DFA and backtracking to the last accepting state when no further transitions are valid."} difficulty="easy"  />

<PracticeProblem client:only="solid-js" question={"What two conditions must hold for a grammar to be LL(1) parseable?&quot; options={[ 'No left recursion and the grammar must be factored (no common prefixes in productions)', 'The grammar must be right-recursive and all productions must have the same length', 'The grammar must be in Chomsky Normal Form', 'The grammar must have exactly one production per nonterminal', ]} correctAnswer={0} explanation=&quot;LL(1) requires: (1) no left recursion ($A \\to A\\alpha$ causes infinite loop in recursive descent), eliminated by $A \\to \\beta A' \\mid \\gamma; A' \\to \\alpha A' \\mid \\epsilon$; and (2) left factoring ($A \\to \\alpha\\beta_1 \\mid \\alpha\\beta_2$ causes ambiguity with one lookahead), eliminated by $A \\to \\alpha A'; A' \\to \\beta_1 \\mid \\beta_2$. After these, the parsing table must have no conflicts."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"In LR parsing, what is the difference between SLR(1), LALR(1), and LR(1) in terms of power and table size?&quot; options={[ 'SLR(1) is least powerful with smallest tables; LALR(1) is medium; LR(1) is most powerful with largest tables', 'All three have identical power but different table construction costs', 'SLR(1) is most powerful; LR(1) is least powerful', 'LALR(1) is more powerful than LR(1)', ]} correctAnswer={0} explanation=&quot;SLR(1) uses global FOLLOW sets for reduce decisions and may incorrectly reject valid strings or miss conflicts. LR(1) carries full lookahead context per state (most precise, largest tables). LALR(1) merges LR(1) states with the same core, losing some precision but keeping tables compact. LALR(1) is used by Yacc/Bison and handles most practical grammars."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"In shift-reduce parsing, a shift-reduce conflict occurs when:&quot; options={[ 'The parser cannot decide whether to shift the next input symbol onto the stack or to reduce by a production', 'Two different reductions are possible at the same state', 'The input is exhausted but the stack is not empty', 'The parser encounters an unexpected token', ]} correctAnswer={0} explanation=&quot;A shift-reduce conflict means the ACTION table entry has both SHIFT and REDUCE for the same state and lookahead. A reduce-reduce conflict means two different productions can be reduced in the same state. SLR(1), LALR(1), and LR(1) progressively eliminate more conflicts. Resolving conflicts requires grammar modification or operator precedence declarations."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"Which FIRST set construction rule is correct for computing FIRST($\\alpha$) where $\\alpha$ is a string of grammar symbols?&quot; options={[ 'If $\\alpha = Y\\beta$ and $\\epsilon \\in \\text{FIRST}(Y)$, then $\\text{FIRST}(\\alpha)$ includes $\\text{FIRST}(Y) \\setminus \\{\\epsilon\\} \\cup \\text{FIRST}(\\beta)$', '$\\text{FIRST}(\\alpha) = \\text{FIRST}(\\text{first symbol of } \\alpha)$ only', '$\\text{FIRST}(\\alpha) = \\text{FIRST}(\\text{last symbol of } \\alpha)$', '$\\text{FIRST}(\\alpha)$ is always a singleton set', ]} correctAnswer={0} explanation=&quot;For $\\alpha = Y_1 Y_2 \\ldots Y_k$: add FIRST($Y_1$) to FIRST($\\alpha$). If $\\epsilon \\in$ FIRST($Y_1$), also add FIRST($Y_2$). Continue until reaching $Y_i$ where $\\epsilon \\notin$ FIRST($Y_i$), or all symbols have $\\epsilon$-derivations (then $\\epsilon \\in$ FIRST($\\alpha$)). This cascading is key to computing FIRST for string arguments."} difficulty="hard"  />

## Intermediate Representations, Optimization, and Code Generation

<PracticeProblem client:only="solid-js" question={"In Static Single Assignment (SSA) form, every variable is defined exactly once. Where are $\\phi$-functions placed?&quot; options={[ 'At dominance frontiers: points where a variable definition from one path meets another path', 'At every basic block entry and exit', 'Only at loop headers', 'Only at function call sites', ]} correctAnswer={0} explanation=&quot;A $\\phi$-function merges values from different control flow paths: $x_3 = \\phi(x_1, x_2)$ means $x_3$ takes $x_1$ or $x_2$ depending on which path was taken. $\\phi$-functions are placed at the dominance frontier of each block that defines a variable. The dominance frontier is exactly where different definitions of a variable can reach the same point."} difficulty="hard"  />

<PracticeProblem client:only="solid-js" question={"What is constant propagation and how does it enable constant folding?&quot; options={[ 'Constant propagation tracks known constant values of variables; constant folding replaces constant expressions with their computed results', 'Constant propagation eliminates unreachable code; constant folding removes dead variables', 'Both are identical optimizations', 'Constant propagation replaces variables with register names; constant folding removes functions', ]} correctAnswer={0} explanation=&quot;Constant propagation (a data-flow analysis) determines that a variable always has a known constant value at a program point. Once propagated, constant folding evaluates expressions involving only constants at compile time: e.g., $x = 10; y = x + 5$ becomes $x = 10; y = 15$. These are often applied together in sequence."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"Register allocation using graph coloring models the problem by building an interference graph where:&quot; options={[ 'Vertices are virtual registers and edges connect simultaneously live variables; coloring with $k$ colors assigns $k$ physical registers', 'Vertices are basic blocks and edges represent data flow', 'Vertices are instructions and edges represent dependencies', 'Vertices are physical registers and edges represent available registers', ]} correctAnswer={0} explanation=&quot;The interference graph has one vertex per virtual register. An edge connects $v_i$ and $v_j$ if they are simultaneously live (one is defined while the other is used later). A valid $k$-coloring assigns $k$ physical registers such that no two interfering virtual registers share a register. This is NP-hard; heuristics (simplify, coalesce, spill) work well in practice."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"What is the key difference between a parse tree and an Abstract Syntax Tree (AST)?&quot; options={[ 'The AST abstracts away punctuation tokens, chains of single-child nodes, and uses operator-specific node types', 'The parse tree is smaller and the AST is larger', 'The AST preserves all grammar productions including whitespace', 'The parse tree uses binary branching and the AST uses n-ary branching only', ]} correctAnswer={0} explanation=&quot;A parse tree preserves every grammar production, including parentheses, commas, and intermediate nonterminals (e.g., $E \\to E + T \\to T + F \\to \\text{id} + \\text{num}$). The AST simplifies this to $\\text{BinOp}(+, \\text{Var}(x), \\text{Num}(42))$, removing syntactic noise. ASTs are used for semantic analysis, optimization, and code generation."} difficulty="easy"  />

<PracticeProblem client:only="solid-js" question={"Which of the following is NOT a valid three-address code instruction?&quot; options={[ '$x = y + z + w$ (more than two operands on the right side)', '$x = y \\text{ op } z$ (binary operation)', '$\\text{goto } L$ (unconditional jump)', '$x = y[i]$ (array access)', ]} correctAnswer={0} explanation=&quot;Three-address code allows at most one operator and at most two operands on the right side of each instruction, plus one result on the left. The instruction $x = y + z + w$ has two operators and three operands, violating the three-address constraint. It would be split into $t_1 = y + z$ and $x = t_1 + w$."} difficulty="easy"  />

## Additional Compiler Questions

<PracticeProblem client:only="solid-js" question={"What is the purpose of the construct lookahead (LL) parsing table conflict check, and what does a conflict indicate?&quot; options={[ 'It verifies that for each (nonterminal, lookahead) pair there is at most one production; a conflict indicates the grammar is not LL(1)', 'It checks for unreachable nonterminals in the grammar', 'It counts the total number of productions in the grammar', 'It verifies that all terminals appear in at least one production', ]} correctAnswer={0} explanation=&quot;An LL(1) parsing table is built by computing FIRST and FOLLOW sets. For each nonterminal $A$ and lookahead terminal $a$, the table should contain at most one production. If FIRST sets of two alternatives for $A$ overlap, or if $\\epsilon$ is in FIRST and FOLLOW sets overlap, a conflict arises. This means no single-token lookahead deterministic parser exists for the grammar."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"In loop optimisation, what is loop-invariant code motion and why is it beneficial?&quot; options={[ 'Moving computations that produce the same value in every iteration outside the loop body, reducing redundant execution', 'Reordering loop iterations to improve cache locality', 'Unrolling the loop to reduce branch overhead', 'Merging multiple loops that iterate over the same range', ]} correctAnswer={0} explanation=&quot;Loop-invariant code motion identifies expressions whose operands do not change across iterations. These expressions are hoisted to a pre-loop block. For example, in a loop where $x = a + b$ is computed but $a$ and $b$ are loop-invariant, $x$ can be computed once before the loop. This reduces the number of instructions executed per iteration and can enable further optimisations on the hoisted code."} difficulty="medium"  />

<PracticeProblem client:only="solid-js" question={"What is SSA form and what must be done when two definitions of the same variable on different control-flow paths converge?&quot; options={[ 'A phi-function is inserted at the convergence point to select the appropriate value based on the incoming control-flow edge', 'The variable is renamed to a completely new name', 'The compiler throws an error for undefined behaviour', 'The older definition is discarded and the newer one is used', ]} correctAnswer={0} explanation=&quot;In SSA form, each variable has exactly one definition. When control flow merges from two paths, each defining a version of variable $x$ (say $x_1$ and $x_2$), a phi-function $x_3 = \\phi(x_1, x_2)$ is placed at the merge point. The phi-function selects $x_1$ or $x_2$ depending on which path was taken. This is a compile-time construct; at runtime it translates to a simple assignment."} difficulty="hard"  />

<PracticeProblem client:only="solid-js" question={"What is the difference between strength reduction and loop unrolling as loop optimisations?&quot; options={[ 'Strength reduction replaces expensive operations with cheaper ones (e.g. multiplication with addition); loop unrolling replicates the loop body to reduce branch overhead', 'They are identical optimisations with different names', 'Strength reduction increases code size; loop unrolling decreases it', 'Loop unrolling requires hardware support; strength reduction does not', ]} correctAnswer={0} explanation=&quot;Strength reduction transforms costly operations into cheaper equivalents. For example, replacing $x * 4$ with $x \\ll 2$ (left shift), or replacing array index multiplication with incremental pointer increments. Loop unrolling replicates the loop body $k$ times and adjusts the loop counter by $k$ per iteration, reducing the overhead of the loop control (branch, increment) and exposing instruction-level parallelism."} difficulty="medium"  />
<PracticeProblem client:only="solid-js" question={"In register allocation, what is the spill problem and how do graph-colouring heuristics typically handle it?&quot; options={[ 'When the number of live variables exceeds the number of physical registers, some variables must be spilled to memory; heuristics choose which variable to spill based on cost', 'When a register holds an incorrect value due to a compiler bug', 'When two variables interfere and cannot share a register', 'When the stack overflows due to excessive recursion', ]} correctAnswer={0} explanation=&quot;Spilling occurs when the interference graph cannot be $k$-coloured with $k$ physical registers. The allocator selects a variable to spill (store to stack memory), removes it from the graph, colours the rest, and inserts load/store instructions around uses of the spilled variable. Spill heuristics consider loop nesting depth, the number of uses, and interference degree to minimise runtime cost."} difficulty="hard"  />

## Common Mistakes

**Confusing lexical analysis with parsing:** Lexical analysis groups characters into tokens. Parsing groups tokens into a syntax tree. They're different compilation phases.

**Assuming all grammars can be parsed deterministically:** Some grammars require backtracking or lookahead beyond one token. LL(1) and LR(1) are restricted grammar classes.

**Forgetting that compiler optimisations must preserve program semantics:** Optimisations can change HOW the program runs but not WHAT it computes. Don't assume all transformations are valid.
