## Coroutines Practice

5 exercises covering structured concurrency, channel communication, flow operators, exception handling, and context switching.

---


### Exercise 1: Structured Concurrency

**Problem:** Write a function that launches three concurrent tasks using structured concurrency. Each task simulates work by delaying for a random duration. The function should wait for all three to complete and return their combined results.

```kotlin
import kotlinx.coroutines.*

suspend fun fetchUserData(): String \{
    delay(100)
    return "UserData"
\}

suspend fun fetchUserPosts(): List<String> \{
    delay(150)
    return listOf("Post1", "Post2")
\}

suspend fun fetchUserFriends(): List<String> \{
    delay(200)
    return listOf("Friend1", "Friend2", "Friend3")
\}

suspend fun loadDashboard(): Triple<String, List<String>, List<String>> =
    coroutineScope \{
        val userData = async \{ fetchUserData() \}
        val userPosts = async \{ fetchUserPosts() \}
        val userFriends = async \{ fetchUserFriends() \}
        Triple(userData.await(), userPosts.await(), userFriends.await())
    \}

suspend fun main() \{
    val result = loadDashboard()
    println(result)
\}
```

**Solution:** `coroutineScope` creates a structured concurrency boundary. All three `async` coroutines run concurrently, and `await()` retrieves each result. If any coroutine fails, the scope cancels all others.

### Exercise 2: Channel Communication

**Problem:** Implement a producer-consumer pattern using Kotlin channels. The producer sends numbers 1 through 10 into a channel, and three consumers compete to receive items. Print each consumed item with its consumer ID.

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

suspend fun producer(channel: Channel<Int>) \{
    for (i in 1..10) \{
        channel.send(i)
        println("Produced: $i")
    \}
    channel.close()
\}

suspend fun consumer(id: Int, channel: Channel<Int>) \{
    for (item in channel) \{
        println("Consumer $id received: $item")
        delay(100)
    \}
\}

suspend fun main(): Unit = coroutineScope \{
    val channel = Channel<Int>(Channel.BUFFERED)
    launch \{ producer(channel) \}
    repeat(3) \{ launch \{ consumer(it + 1, channel) \} \}
\}
```

**Solution:** `Channel.BUFFERED` provides a default buffer. The producer sends values then closes the channel. Three consumers iterate over the channel using the `for (item in channel)` idiom, which terminates when the channel is closed and empty.

### Exercise 3: Flow Operators

**Problem:** Create a Flow that emits integers from 1 to 20. Apply operators to filter only even numbers, map them to their squares, take only the first 5, and collect the results.

```kotlin
import kotlinx.coroutines.flow.*

suspend fun main() \{
    val result = (1..20).asFlow()
        .filter \{ it % 2 == 0 \}
        .map \{ it * it \}
        .take(5)
        .toList()
    println(result)
\}
```

**Solution:** `asFlow()` converts the range to a cold Flow. `filter` keeps even numbers (2, 4, 6, ...). `map` squares each (4, 16, 36, ...). `take(5)` limits to the first 5 emissions. `toList()` collects into a list: `[4, 16, 36, 64, 100]`.

### Exercise 4: Exception Handling in Coroutines

**Problem:** Write a coroutine that handles exceptions gracefully. Use a `SupervisorJob` so that a failure in one child coroutine does not cancel its siblings. Demonstrate that sibling coroutines continue running after one fails.

```kotlin
import kotlinx.coroutines.*

suspend fun main(): Unit = coroutineScope \{
    val supervisor = SupervisorJob()
    val scope = CoroutineScope(supervisor + Dispatchers.Default)

    scope.launch \{
        delay(100)
        println("Child 1: working")
        throw RuntimeException("Child 1 failed")
    \}

    scope.launch \{
        delay(200)
        println("Child 2: working")
        delay(200)
        println("Child 2: completed")
    \}

    scope.launch \{
        delay(300)
        println("Child 3: working")
        delay(200)
        println("Child 3: completed")
    \}

    delay(1000)
    supervisor.cancel()
\}
```

**Solution:** `SupervisorJob` prevents child failures from propagating to the parent and siblings. Child 1 fails at 200ms, but children 2 and 3 continue independently. Without `SupervisorJob`, the failure of child 1 would cancel the entire scope.

### Exercise 5: Context Switching with `withContext`

**Problem:** Write a function that performs a CPU-intensive computation on `Dispatchers.Default`, switches to `Dispatchers.IO` for a simulated network call, then switches back to `Dispatchers.Default` for result processing. Log the thread name at each step.

```kotlin
import kotlinx.coroutines.*

suspend fun processData(): String = withContext(Dispatchers.Default) \{
    println("Step 1 - CPU work on: $\{Thread.currentThread().name\}")
    val data = computeOnDefault()

    val result = withContext(Dispatchers.IO) \{
        println("Step 2 - IO work on: $\{Thread.currentThread().name\}")
        simulateNetworkCall(data)
    \}

    withContext(Dispatchers.Default) \{
        println("Step 3 - Process on: $\{Thread.currentThread().name\}")
        processResult(result)
    \}
\}

fun computeOnDefault(): String \{
    var sum = 0L
    for (i in 1..1_000_000) sum += i
    return "computed:$sum"
\}

suspend fun simulateNetworkCall(data: String): String \{
    delay(500)
    return "response for $data"
\}

fun processResult(result: String): String = "processed: $result"

suspend fun main() \{
    val output = processData()
    println(output)
\}
```

**Solution:** `withContext` switches the coroutine's dispatcher for a specific block while maintaining structured concurrency. The thread name changes between steps, demonstrating the context switch. The coroutine resumes on the original context after `withContext` completes.

## Intuition

**Coroutines are lightweight threads for asynchronous programming:** Instead of blocking a thread while waiting for I/O, coroutines suspend execution and resume when the result is available. This enables handling thousands of concurrent operations with minimal resources.

**Why it matters:** Coroutines simplify asynchronous code that would otherwise require complex callback chains or reactive streams.

**The key insight:** Structured concurrency ensures that coroutines are properly cancelled and cleaned up — preventing memory leaks and orphaned background work.

## Common Mistakes

**Launching coroutines without a scope:** Coroutines must be launched within a CoroutineScope. Using GlobalScope leaks coroutines that survive beyond their intended lifecycle. Always use structured concurrency with appropriate scopes.

**Confusing `launch` with `async`:** `launch` returns a Job (no result). `async` returns a Deferred (awaitable result). Use `launch` for fire-and-forget work. Use `async` when you need the result. Mixing them up leads to either missing results or unnecessary waiting.

**Forgetting to handle coroutine exceptions:** Uncaught exceptions in coroutines propagate to the CoroutineScope and cancel all sibling coroutines. Always use `CoroutineExceptionHandler` or try-catch inside the coroutine to handle errors gracefully.
